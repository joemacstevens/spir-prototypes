1 · What's new in the app

The paywall doesn't exist in-app yet — this is a net-new PaywallPanel prefab loaded by SingletonBehaviourUI. No existing screens are modified.

Trigger points (decide later): from the home screen "Upgrade" tab, from any locked Max-only feature (XP gates, AI insights), and from onboarding completion. AJE-12 (XP Payment Gates) blocks on this paywall design — once you pick a direction, the XP gate popup falls back here.

2 · Annotated breakdown

1
Header — back chevron + title
Standard panel header. Back chevron pops the panel via SingletonBehaviourUI.Hide. Title is a TextMeshProUGUI, static.
2
Feature comparison table
A VerticalLayoutGroup containing one FeatureRow sub-prefab per feature. Each row is a 3-column horizontal layout: feature name (TMP), Pro state, Max state. The header row is a static prefab pinned at the top.
3
Max column highlight
A semi-transparent Image behind the entire Max column, tinted purple. Lives behind the table content; uses RectTransform anchors to span the column's width × full table height.
4
Cell content — check / em-dash / qualitative
Each cell is either: a checkmark Image, an em-dash TMP, or a short string ("Up to 3", "Unlimited"). The FeatureRow script exposes a CellContent enum so designers can swap in the editor.
5
CTA pair — secondary + primary
Two Buttons in a HorizontalLayoutGroup. OnClick → PaywallPanel.OpenStripe(tier, period) which runs Application.OpenURL($"…/dashboard?subscribe={tier}&period={period}").
6
Mini rating row
Five Unicode stars (or 5x small Images) + TMP for "4.8 · 250K reviews". Static today; could be backend-fed later.

3 · Unity implementation notes

Two clean approaches to the feature table:

  • A — static prefab (recommended). Bake all FeatureRow instances into the PaywallPanel prefab in editor. No runtime data. Works as long as features change < once per quarter.
  • B — dynamic. PaywallPanel.cs reads a FeatureCatalog ScriptableObject and instantiates rows at Awake. Better if marketing wants to A/B feature copy without a build.
Recommendation: ship A. The catalog won't change weekly, and a dev-driven prefab is one less moving part for QA.

Sticky table header inside a ScrollRect: pin the header row outside the scroll content (sibling to ScrollRect.content, anchored to the top of the panel). Standard UGUI pattern, no custom math.

6 · Why we'd pick V1

If your "comparative analysis" comment is the dominant signal — and the user persona is someone who wants to compare and decide on the merits — V1 is the most honest interpretation. It's also the cheapest to ship and has zero data dependencies, so it can land on the next sprint with no backend coordination.

The risk: it doesn't sell. There's no narrative, no social proof, no anchoring. If users are bouncing off the upgrade page, the data will tell us, and we'd graduate to V2 or V3 in a follow-up.

3 · Unity implementation notes

Star rating math: stack two Images per star — gray background star + gold foreground with Image.Type=Filled, fillMethod=Horizontal, fillAmount=0–1. Five stacks. To render 4.8: stars 1–4 fillAmount=1.0, star 5 fillAmount=0.8. Trivial and precise.

Testimonial data source — pick one:

  • A — hardcoded array (recommended now). PaywallPanel.testimonials is a serialized struct array, instantiated at Awake.
  • B — TestimonialCatalog ScriptableObject. Better if non-engineers want to edit copy.
  • C — backend-driven via NetworkAPImanager.cs. Overkill until reviews are an actual product feature.

Sticky bottom CTA: place outside the ScrollRect, anchored to the bottom of the canvas. Add a transparent spacer at the end of the scroll content equal to CTA height so the last testimonial isn't occluded.

Bonus reuse: if AJE-12 (XP Payment Gates) builds an XP-spend popup that falls back to a paywall, V2's testimonial card prefab can be reused there as a "see what others say" rail. One prefab, two surfaces.

3 · Unity implementation notes

Phone vs tablet layout: two clean paths —

  • A — single VerticalLayoutGroup always. Cards stack on phone and tablet. Loses the side-by-side affordance on tablet but ships fastest.
  • B — script-switched orientation. A LayoutGroupOrientationSwitcher watches canvas width; below 600pt = vertical, above = horizontal. ~30 lines of code.

Recommend A for first ship — most SPiR usage is portrait phone anyway. Graduate to B if tablet usage > 5% of sessions.

"Best Value" ribbon: bake the 25° rotation into the sprite asset (export rotated). Rotating at runtime causes ugly anti-aliasing on Adreno GPUs, which we've seen on the Pixel 6a / Galaxy A series mentioned in the test rig list.

Trial hook flag: the trial badge is a single GameObject controlled by PaywallPanel.trialActive. If you say no to the trial in the BLOCKING questions, set the flag false and the whole UI element disappears with no further code. Same for the annual toggle if monthly-only.
